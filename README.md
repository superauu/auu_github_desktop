# AuuGit

[简体中文](README.md) · [English](README.en.md)

一个基于 Tauri、React 和 TypeScript 的桌面 Git 客户端，把日常 Git 操作、可视化分支管理、GitHub 协作和 AI 辅助放进同一个工作区。

AI 用于解释变更、生成说明和提供建议；应用不内置自主编码 Agent。

[下载安装包](https://github.com/superauu/auu_github_desktop/releases/latest) · [反馈问题](https://github.com/superauu/auu_github_desktop/issues)

“多仓库总览”集中读取已打开及最近使用仓库的分支、改动文件数、冲突、进行中的 Git 操作及同步计数。每批最多显示 24 个仓库，最多同时读取 3 个，支持名称/路径搜索、计数芯片一键筛选（需要处理/待推送/冲突，可再点恢复）、逐仓库重试与停止刷新；失败仓库单独显示错误，未授权仓库通过明确入口授权后读取。同步计数来自本机已获取的远端引用，刷新总览不会自动 fetch。CI 使用当前 GitHub 账号，汇总跟踪远端提交的 Checks 与传统状态，显示分支和提交号，结果不完整时明确标记；CI 链接指向被检查提交，未推送的本地提交不包含在结果内。切换账号会丢弃旧结果。可从仓库行直接进入对应仓库的变更或历史，未打开仓库时也能从欢迎页或命令面板进入总览。

“最近操作”在本机跨会话保存最近 100 条、最多 30 天的操作与通知，包括仓库、时间、结果、耗时及限长详情。持久化前过滤常见凭据格式，不保存动作回调；重启后可搜索、按仓库/错误筛选、复制诊断或进入恢复中心，不会恢复旧重试按钮。清空会同时删除本机保存内容；存储不可用时提示并保留当前会话功能。

## 主要功能

| 功能 | 说明 |
| --- | --- |
| 多仓库工作区 | 使用标签页切换仓库，管理本地分支、远程分支、标签、Stash 和 Worktree。 |
| 变更与提交 | 查看文本差异，按文件、代码块或变更行暂存；通过分组整理提交。 |
| 可视化分支操作 | 在提交图中拖动分支标签，预览合并或变基；拖动提交到当前分支以 Cherry-pick。 |
| 历史整理与恢复 | 对尚未发布的线性提交排序、Squash 或 Fixup；使用恢复点与 Reflog 查看差异、找回提交。 |
| 图片对比 | 并排或叠加查看图片变更，调整叠加透明度。 |
| 历史搜索 | 按提交信息或代码增删内容搜索。 |
| GitHub Pull Requests | 查看、创建、审查和合并 PR，生成 PR 描述。 |
| GitHub Issues | 搜索和筛选 Issue，创建编辑、管理标签与负责人、发表评论、关闭与重开；从 Issue 创建本地分支、创建关联 PR，并在 Issue 与 PR 之间跳转。 |
| GitHub Actions | 查看工作流、运行记录、Jobs 和步骤，获取已完成任务的日志，触发、重跑或取消运行。 |
| AI 辅助 | 生成提交说明，解释提交和分支差异，诊断 Git 错误，建议文件分组和冲突解决内容。 |
| 代码审核 | 在工作区变更中按文件或代码块审核、记录和解决意见，并汇总带原始代码上下文的 AI 修复报告，支持预览和复制。提交前默认提醒未审核内容，可继续提交，也可在 Git 设置或提醒中关闭。[使用指南](docs/review-guide.md)。 |
| 个性化 | 中英文界面、主题、紧凑模式、布局调整和光标主题。 |

手动运行 GitHub Actions 时，会从所选分支读取工作流定义，显示必填项、默认值和选项；环境参数可填写仓库中配置的环境名称。加载失败时可重试，不会提交旧分支的参数。

Issues 与 PR 使用同一个 GitHub 协作远程和账号。Issue 页面支持状态、标题/正文、完整标签名和负责人登录名筛选，每页 30 条；搜索最多浏览前 1000 条，结果不完整时会提示缩小范围。描述与评论以安全纯文本展示，编辑时保留 Markdown 原文。标签与负责人从仓库已有选项中选择；实际写入权限由 GitHub 校验，失败时保留草稿。

“从 Issue 创建分支”允许选择起点及是否切换，Issue 与本地仓库/分支的对应关系保存在本机；以后从该分支创建 PR 时会带入 Issue，也可直接点击“创建关联 PR”或在 PR 表单中搜索选择多个 Issue。选中的 Issue 以明确的 `Closes owner/repo#编号` 写入 PR 描述；这是 GitHub 的[关闭引用](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)，通常需要合并到默认分支后才关闭，应用不会在创建或合并 PR 时直接将 Issue 标记完成。跨仓库引用保留完整仓库名。

Issue 详情根据 GitHub 时间线显示提及它的 PR；PR 页面和评审弹窗显示描述中引用的 Issues。同一协作仓库内可直接跳转，其他仓库在 GitHub 打开。回到 Issue 或点击刷新可读取实际关闭/重开状态。Alt+6 和命令面板均可打开 Issues。评论与时间线沿用分页读取上限，各最多读取 1000 条。

已关联的分支会在顶部显示“当前任务”，切换分支时同步切换。已有分支也可从 Issue 详情中关联；解除关联只影响本机记录。“根据 Issue 拟提交说明 / PR 草稿”使用本地模板，预览确认后才替换草稿，不会声称已完成验证。生成说明默认只参考代码改动；勾选“生成说明时参考 Issue 背景”后，最多前 5 个关联 Issue 的标题与限长描述会参与生成。使用外部模型时，这些背景会发送至已配置的模型服务；提交说明使用 `Refs`，PR 的关闭引用仍由关联选择决定。

Issue 详情按需加载关联 PR 的当前提交、合并状态和评审意见，同时汇总 [Checks](https://docs.github.com/en/rest/checks/runs) 与[传统提交状态](https://docs.github.com/en/rest/commits/statuses)。每种 CI 接口最多显示 100 条，超限或读取失败时提示状态不完整；跳过、中立、取消和超时不会显示为全部通过。评审摘要不代替 GitHub 的合并规则。可见窗口每分钟及重新聚焦时刷新，保留未发送的评论，编辑弹窗和写操作期间暂停定时刷新。合并会校验用户看到的 PR head SHA，并在成功后立即及短暂延迟后重读关联任务状态，适应 GitHub 的异步关闭处理。

推送时可选择 remote 和目标分支，窗口会显示仓库地址与推送方向。默认目标遵循分支 `pushRemote`、仓库 `remote.pushDefault` 和跟踪配置；“记为默认推送远程”与“设置跟踪分支”分别控制推送目标和后续拉取来源。“提交并推送”会先选择目标，取消时不会创建提交。标签推送和远程标签删除也支持选择 remote。

远程分支右键菜单支持删除服务器上的分支，确认框显示目标仓库与分支，本地分支保留。工具栏获取会更新所有 remote；更多操作及远程管理中可获取并清理失效远程引用。在设置的远程管理中，可独立选择 PR / Actions 对应的 GitHub remote。领先与落后数量始终相对于状态栏显示的跟踪分支。创建 PR 时可选择来源 GitHub 仓库及已发布的远程分支名，支持跨 fork 的同名分支；切换协作仓库后会重新加载目标分支。推送成功后若默认远程偏好保存失败，会单独警告，保留推送成功结果。

提交面板在常见笔记本宽度下默认与差异并排显示，也可在外观设置中选择自动、并排或抽屉模式。分支、PR 和工作流列表支持键盘移动与确认，分支行可用 Shift+F10 打开操作菜单。仓库工具集中提供恢复中心和诊断。推送偏好与跟踪设置位于高级选项；错误提示先显示处理建议，技术详情仍可展开查看和复制。

“AI 规划全部变更”使用已配置的 AI 分析已暂存、未暂存及新文件，建议提交数量、顺序、分组理由和每个提交的标题与说明。确认前可移动文件、编辑说明、调整顺序或合并分组；确认后批量创建提交，也可先选远程目标，在全部提交成功后推送一次。当前按完整文件拆分，部分暂存文件会使用完整工作区版本。分析后内容变化会阻止执行；中途失败保留已完成的提交并报告剩余操作，推送失败只重试推送。原有提交草稿保持不变。

“按暂存代码块规划提交”支持手动将同一文件的多个代码块分配到不同提交。先按文件、代码块或变更行暂存，再编辑各组标题与说明、排序、合并，并预览相对于上一组的实际提交差异。未分配的块继续暂存，未暂存内容不纳入提交；新增、删除、重命名、二进制和权限变化作为整体处理。执行使用后端生成的临时索引，保留原暂存选择；分支、HEAD 或暂存区变化会阻止后续提交。钩子照常运行，失败或改变提交内容时停止并报告实际完成的提交；可请求在当前提交结束后停止。已有 HEAD 时自动保留恢复点。重新读取剩余改动会清空分组；推送使用原有推送入口。本轮提供手动规划。

代码块规划的分组、顺序、标题与说明会自动保存为本机草稿，按仓库和分支隔离，保留最近 20 份、最多 30 天。草稿仅保存说明、代码块 ID 和快照摘要，不保存源代码差异或临时索引。关闭或重启后重新打开规划时，先读取当前 Git 状态；HEAD、暂存内容或代码块变化时禁止恢复旧分配。匹配的草稿需点击“恢复草稿”才应用，恢复后可继续编辑，提交仍需另行确认。重新读取或开始创建提交会清除对应草稿，避免重复执行；本机存储失败时会提示，手动规划仍可使用。

代码块规划器可查看当前分支关联 Issue 的状态和限长背景，为选中的提交预览并添加 `Refs owner/repo#编号`。预览显示完整说明，应用前再次核对暂存快照、Issue 关联和账号；取消或失败保留原说明。引用作为说明正文随规划草稿保存，恢复后可继续编辑，替换 AI 分组后应重新核对。重复的实际引用会跳过，代码示例与注释中的引用不计入；说明超长或代码块/注释未闭合时会提示修正。创建 PR 沿用分支的 Issue 关联，关闭引用在 PR 中单独选择。详情加载失败时仍可按已关联编号添加引用，手动规划保持可用。

代码块规划中的“AI 建议分组”按需将暂存快照的完整代码块清单及差异摘录发送给已配置的模型，建议提交数量、顺序、标题、说明和分组依据。AI 分析最多 200 个块、20,000 字符清单、60,000 字符输入，每块差异最多 6,000 字符；截取时明确提示。模型必须将每个块恰好分配一次，遗漏、重复、未知 ID 或无效说明会被拒绝。建议先预览，明确“应用建议并替换当前分组”后才替换手动分组，应用后仍可编辑、留存部分块及逐组预览，创建提交另行确认。分析前后及应用前核对快照；取消、失败、设置变化或过期响应保留原分组。未配置模型时仍可手动规划。分析复用现有 AI 协议适配器，60 秒超时，不自动创建或推送提交。

Git 写操作会在状态栏显示当前操作、已用时间和排队数量。“取消排队”只跳过尚未开始的任务，正在执行的操作会继续完成。主视图出现渲染异常时，可重试或复制诊断信息；重新加载整个窗口前请先保存编辑内容。

恢复中心支持为手动恢复点填写名称、给已有恢复点改名或删除。名称保存在仓库本地配置中，关联 Worktree 共享名称；留空则显示默认名称。删除只移除所选恢复点，不改变分支或工作区文件；如果没有其他引用保留相关提交，这些提交以后可能被 Git 清理。

变更列表的文件复选框只负责勾选批量操作的文件：勾选后可统一暂存、取消暂存或忽略，Shift 勾选连续选择。暂存单个文件使用行尾的加号/减号按钮、空格键或右键菜单。“未跟踪文件”分区的“全部添加”可一键跟踪并暂存全部新文件。

合并、变基与历史整理提供预览或恢复机制。历史整理会阻止改写已存在于已获取远程分支上的提交；操作前请先获取远端更新。

## 安装与使用

当前发布流程提供三平台安装包：**Windows x64**（安装包 / MSI / 独立可执行文件）、**macOS**（Intel 与 Apple Silicon 的 dmg）和 **Linux**（AppImage / deb / rpm）。发布流程支持 Windows、macOS 和 Linux AppImage 的签名自动更新；对应平台的更新产物与签名需要成功上传并写入更新清单。使用 deb / rpm 或未收到更新时，请从 Releases 手动下载新版本。

1. 安装 [Git](https://git-scm.com/downloads)，并确保应用能够找到 Git。
2. 在 [Releases](https://github.com/superauu/auu_github_desktop/releases/latest) 下载对应平台的安装包：Windows 为 `AuuGit_<版本>_x64-setup.exe`（或 MSI），macOS 为 `<版本>_x64.dmg`（Intel）或 `<版本>_aarch64.dmg`（Apple Silicon），Linux 为 AppImage、deb 或 rpm。
3. 打开已有仓库或克隆仓库。GitHub 协作功能可通过应用中的账号设置连接 GitHub。

Release 中的 `auugit.exe` 是 Windows 独立可执行文件。需要自动升级时，建议使用安装包版本。

### 自动更新

桌面应用启动约 15 秒后检查新版本，发现更新后在状态栏保留入口。可以查看版本说明、选择下载并查看进度，或稍后处理。下载完成后，点击“安装并重启”并确认才会安装；有仓库 Git 任务尚未结束时会阻止安装。安装前请先保存编辑内容。更新包通过签名验证；版本信息由 Release 中的 `latest.json` 提供。

浏览器开发模式不执行桌面应用更新。检查失败时，可从 Releases 手动下载安装包。

### 后台刷新与最近操作

活跃窗口每 10 秒检查外部变更，空闲 2 分钟后降至每 30 秒，空闲 5 分钟后降至每 60 秒。隐藏窗口和正在执行 Git 写操作的仓库会跳过后台检查；重新聚焦时合并触发刷新。相同差异会复用解析结果，连续编辑即使 Git 状态码相同也会重新读取。

状态栏的“最近操作”保留本次会话最近 100 条 Git 写操作与通知，可筛选失败、复制详情、重试失败的获取操作，或打开对应仓库的恢复中心。耗时包含排队等待；记录不写入磁盘，关闭应用后清空。

### AI 设置

提交说明和 PR 描述支持本地规则或模板，无需 API Key。需要模型生成、变更解释或冲突建议时，在设置中选择自定义大模型 API，再选择服务支持的协议：**OpenAI Chat Completions、OpenAI Responses 或 Anthropic Messages**。填写对应的接口地址、模型名称和 API Key，使用“测试连接”验证配置。

地址可以填写 Base URL（例如 `https://api.openai.com/v1`、`https://api.anthropic.com/v1`），也可以填写完整接口路径。旧配置默认使用 Chat Completions；切换协议会保留已有地址、模型和密钥，请按服务要求调整。

浏览器开发模式通过本机开发服务器转发 AI 请求，以兼容不支持浏览器跨域访问的服务。OpenCode Go 请求会自动附带 AuuGit 客户端标识和本次应用会话的稳定 ID，无需手动填写请求头。

调用外部模型时，相关代码、差异或错误上下文会发送到你配置的服务。桌面端的 GitHub Token 和 AI API Key 使用系统凭据存储；浏览器开发模式仅在内存中保留凭据。AI 生成内容应在应用或提交前核对。

## 本地开发

准备以下环境：

- Node.js 20.19+、22.13+ 或 24+ 及 npm。
- Git。
- 构建桌面端时需要 Rust stable，以及对应平台的 [Tauri 开发依赖](https://v2.tauri.app/start/prerequisites/)。Windows 需要 Microsoft C++ Build Tools 和 WebView2。

```sh
git clone https://github.com/superauu/auu_github_desktop.git
cd auu_github_desktop
npm ci
```

启动浏览器开发模式：

```sh
npm run dev
```

打开 `http://localhost:5173`。开发服务器包含访问本机仓库的接口，请仅在本机使用。Git 操作会作用于你选择的真实仓库。

开发接口默认只允许访问本项目目录及其子目录。需要访问其他仓库时，在启动前配置 `AUUGIT_DEV_ROOTS`；多个目录使用系统路径分隔符（Windows 为分号）分隔，例如 PowerShell：`$env:AUUGIT_DEV_ROOTS='E:\code\auu_github_desktop;E:\repos'`。目录范围也会检查符号链接和新建目录的已有父目录。

桌面应用通过原生目录选择器记录授权路径；手工输入或恢复旧版本保存的路径时，首次访问需要确认，后续启动会记住选择。文本编辑与忽略规则文件限 8 MiB；保存会检查原内容并原子替换，应用内写入串行执行。外部程序在最后一次检查与替换之间修改文件的极短窗口仍然存在。

开发端只接受服务器 PATH 中的 Git，或启动前通过 `AUUGIT_GIT_BINARY` 指定的程序；网页传入的同名 `git.exe` 不会自动获得执行权限。桌面端首次使用自定义 Git 路径时会显示原生确认框。已授权的仓库文件夹可在“设置 → Git”中撤销，撤销后重新打开需要再次确认。

启动桌面开发模式：

```sh
npm run tauri -- dev
```

验证与构建：

```sh
npm test
npm run lint
npm run check:release
npm run build
npm run tauri -- build -- --locked
```

`npm run build` 生成前端文件；桌面安装包通过最后一条命令生成，位于 `src-tauri/target/release/bundle/`。带自动更新签名的构建还需要匹配应用公钥的签名私钥配置。

视觉回归使用 `npm run test:visual`：首次运行前执行 `npx playwright install chromium`。Windows CI 会检查明暗主题及三种窗口尺寸，失败时保存截图差异与浏览器跟踪；基线审阅和其他平台的运行说明见 [视觉回归指南](tests/visual/README.md)。

凭据存储按平台启用：Windows Credential Manager、macOS Keychain、Linux keyutils 与 Secret Service。Linux 运行时需要可用的 Secret Service 和会话 D-Bus。当前发布和桌面回归验证仍以 Windows x64 为准。

## 发布新版本

1. 运行 `node scripts/bump-version.mjs <新版本>` 一次改齐 `package.json`、`package-lock.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml` 和 `src-tauri/Cargo.lock` 中的应用版本号，并自动复跑版本校验。
2. 编写 `releases/v<新版本>.md` 发版说明（tag 构建会硬校验其存在且非空；缺失时 `check:release --require-notes` 也会提前拦截）。
3. 运行测试、版本校验和前端构建。
4. 配置 GitHub Actions Secrets：`TAURI_SIGNING_PRIVATE_KEY` 与 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`，并保持私钥与应用内更新公钥匹配。
5. 推送匹配应用版本号的 `v<版本>` 标签。Windows 发布工作流会构建、签名并上传安装包及更新清单到 GitHub Release；macOS 与 Linux 构建矩阵会把对应平台安装包挂载到同一个 Release，并把可用的 macOS 与 Linux AppImage 更新签名合并进 `latest.json`。缺失签名的平台会被跳过，发布后需核对更新清单。

手动触发构建会生成 Actions 构建产物；只有推送版本标签才会执行当前流程中的 Release 发布步骤。
