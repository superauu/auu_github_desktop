# AuuGit v0.13.1 · 平台差异收尾

本版清掉 v0.13.0 真机联调遗留的三项平台差异：GitLab 合并请求的改动统计、Gitee 评审状态的可读化、Gitee 可指派人的退化候选。

## GitLab 改动统计不再恒为 +0 -0

- GitLab 的 MR 列表 / 详情 API 均不携带增删行数字段（GitHub / Gitea / Gitee 列表自带或透传），此前 MR 详情「代码改动统计」恒显示 `+0 -0`。
- 现在列表对象缺统计字段时，选中 MR 后自动拉取一次文件清单求和回退显示（增删行数 + 文件数）；列表自带统计的平台行为不变。求和逻辑抽为纯函数 `sumPullStats` 单测锁定。

## Gitee 评审状态可读化

- 真机对照实验钉死公开 v5 语义：`POST /review`（批准）在公开 API **无处可读**——评审记录列表端点不存在（HTML 404），批准也不落在 testers 或评论里；而 `testers[].accept`（指定测试工程师的「测试通过」标记）**只随 `POST /test` 端点翻转**。
- 评审列表现从 PR 详情的 `testers[].accept === true` 映射 `APPROVED` 记录，评审状态徽标不再恒为 PENDING。
- 「批准」动作在 POST review 后 best-effort 同步 POST test（非指定测试工程师时 403 静默忽略，批准本身不受影响），批准 → 读回形成读写闭环——真机端到端验证：批准后评审列表即刻返回 APPROVED。
- 附带收益：批准即满足私有仓库的合并测试门控（合并流程本就要先 test 再 merge）。

## Gitee 可指派人退化候选

- 公开 v5 无任何成员列表路由（collaborators / members / assignees / warehouse_members 实测均 HTML 404），可指派人列表从空数组退化为**仓库所有者单人候选**（owner 必然可指派，写路径真机验证过）；新建/编辑 Issue 的指派选择器可正常渲染。

## 测试

- node 全量 **725**、Rust 测试 74 + clippy `-D warnings`、e2e integrations **3** 全绿；新增 Gitee 评审/指派人契约用例与 `sumPullStats` 聚合用例，评审读取与批准闭环经真实 gitee.com API 端到端验证（测试仓库已删）。

---

Version 0.13.1 clears the three platform gaps left by the v0.13.0 integration round: GitLab merge-request diff stats now aggregate from the files list when the list API lacks additions/deletions (GitHub/Gitea/Gitee lists carry the fields natively), Gitee review state becomes readable — a live controlled experiment pinned that `POST /review` approvals are unreadable in public v5 while `testers[].accept` flips only via `POST /test`, so reviews map accept===true testers to APPROVED and the approve action best-effort also calls the test endpoint, closing the write-read loop (verified end-to-end against gitee.com) — and the Gitee assignee picker degrades from an empty list to the repository owner as a single candidate since public v5 has no member-listing route (collaborators/members/assignees all return HTML 404). Test base: 725 node, 74 Rust, clippy clean, 3 e2e integration specs.
